# Platform Styling Audit

**Method:** UI/UX Pro Max skill (`ui-ux-pro-max`), read-only. No CSS/HTML/token changes were made in this pass.
**Scope:** 16 HTML surfaces (`index.html`, `master.html`, `whitecell.html`, `sme.html`, `teams/{blue,green,red,industry}/{scribe,facilitator,notetaker}.html`) and the full stylesheet cascade under `styles/`.
**Token baseline:** `styles/base/variables.css` (~250 custom properties), read first and treated as the intended system; every other file is measured against it.

## 1. Summary

**Token-system health:** Mixed. `variables.css` itself is well-organized and mostly complete (color, type, spacing, radius, shadow, z-index, motion, team-accent scales all exist, and dark mode is implemented correctly as token re-pointing). The problems are almost all **downstream of the token file**: page and component CSS added later (`pli-sme.css`, `scribe.css`, `loader.css`, `sidebar.css`) forked components, invented parallel tokens, or referenced tokens that don't exist — and because these forks happen to produce similar-looking colors today, they've gone unnoticed. The system reads as coherent at a glance but is fragile under any single-token edit.

**Top 5 systemic issues:**

1. **The loading/spinner component is forked.** `styles/components/modals.css` and `styles/components/loader.css` both define `.spinner`, `.loader-overlay`, `.loader-content`, `.loader-message`, `.inline-loader-message`, and `.skeleton` with different visual designs and different token choices, and `loader.css` is only `<link>`ed on 10 of the 16 surfaces. The result: the *same* loading spinner renders as a circular two-tone ring on `whitecell.html`, `sme.html`, and all four `notetaker.html` pages, and as a rotating-square "cypher" spinner with a gold pulsing center everywhere else. See Finding G1.
2. **Two parallel token scales for the brand green.** `--color-navy*` and `--color-primary-*` carry four identical values (`--color-navy` ≡ `--color-primary-500`, `--color-navy-deep` ≡ `--color-primary-700`, `--color-navy-soft` ≡ `--color-primary-100`, `--color-navy-strong` ≡ `--color-primary-200`) but different files pick different families with no documented rule for which is canonical. See Finding I3.
3. **Duplicate layout-primitive class definitions.** `.section-header` (`app-layout.css` vs `sidebar.css`) and `.empty-state`/`.empty-state-icon`/`.empty-state-title` (`cards.css` vs `sidebar.css`) are each defined twice with different visual rules; whichever file loads later wins, so the same class renders differently depending on which surface it's on. See Findings I1, I2.
4. **"Phantom tokens"** — `var(--name, #fallback)` references where `--name` is never defined anywhere in the codebase, so the fallback hex silently becomes the permanent value: `--color-primary` (pli-sme.css), `--color-warning-soft` / `--color-warning-ink` (sidebar.css), and `--font-size-xs` / `--font-size-lg` (scribe.css, which has **no** fallback and so fails open). See Findings G3–G5.
5. **No dark-theme treatment for the PLI/SME review surfaces and the Scribe presentation deck.** Both `pli-sme.css` and large parts of `scribe.css` use raw hex/rgba (a second red `#b04a4a`, a second dark green `#0a4d28`, a third blue `#1c54a3`, a bare white chart card) that never repoint for `[data-theme="dark"]`, unlike literally everything else in the design system. See Findings G6, G9.

**Overall read:** The base token file is trustworthy; the component and page layer is not fully reconciled with it. Nothing found is a catastrophic failure (colors are close enough that the drift is easy to miss at a glance), but the loader fork (Issue 1) and the duplicate token scale (Issue 2) are structural and will keep causing small, hard-to-explain visual differences between surfaces until resolved.

## 4. Open questions

1. **Which token scale is canonical, `--color-navy*` or `--color-primary-*`?** They share four identical values today (Finding I3), but nothing documents which one new components should reach for. (Competing options: keep both and alias one to the other; deprecate `--color-primary-*` since `--color-navy*` has the more complete family of derived shades; deprecate `--color-navy*` since `--color-primary-*` follows the more conventional numeric-scale naming other tokens use.)
2. **Was `pli-sme.css` (and parts of `scribe.css`) originally designed against a different, blue-accented version of this system?** The blue/navy fallback values (`#1d4ed8`, `#1f3b6e`) and the standalone blue wash (`rgba(28,84,163,…)` in `scribe.css`) don't correspond to any current W&M-green token, which reads like a leftover from an earlier palette rather than a deliberate distinct accent (Findings G9, I17, A2 material).
3. **Should `--color-warning-soft` / `--color-warning-ink` become real tokens (with dark variants), or should `.sidebar-badge--awaiting` simply reuse the existing `--color-warning-100` / `--color-warning-700`?** Right now neither option is in effect — the code references tokens that don't exist and silently uses their fallback forever (Finding G4).
4. **Is the dark-mode primary-button contrast shortfall a signed-off trade-off or a bug?** `variables.css:332-334`'s own comment states "white-on-green button labels sit a touch under AA (the common dark-theme tradeoff for a coloured primary CTA)" — is that acceptable long-term, or should `--color-navy` (dark) be darkened/lightened to clear 4.5:1 with white text?
5. **Is the green team's "connected" indicator dot (`#34c759`) intentionally distinct from `--color-team-green` (`#4a7c59`), or should it be unified?** The inline comment in `header.css:392-395` claims intent ("kept distinct... so the team reads at a glance"), but this creates the only instance in the system where a single team has two different "team colors" depending on which component you're looking at (Finding I9).
6. **Should `.content-section`'s default-hidden state move into CSS** (mirroring the `.section-content.active` pattern already used in `sidebar.css`), now that the same inline `style="display:none"` has been hand-copied onto 78 elements across 11 files? Or is there a technical reason (e.g. avoiding FOUC before JS attaches) that requires it to stay inline? (Finding G8)
7. **Is the landing page's lack of a manual theme toggle intentional?** `setupThemeToggle()` only mounts into `.header-actions`, which `index.html` doesn't have (Finding G7) — confirm whether the login screen is meant to always follow the OS theme, or whether it's missing a toggle by omission.
